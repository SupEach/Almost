## 1. 先建立正确的工作方式

**一个任务对应一个可以验收的结果；长期决定写进仓库；新任务从当前代码恢复上下文。**

不要把“首页开发”“网站完善”作为无限延长的任务。可以保留首页这个分类，但实际执行应拆成“首页 / 移动菜单修复”“首页 / 精选作品替换”等有终点的任务。

项目采用以下依据顺序：

1. 你最新明确提出的要求。
2. [AGENTS.md](C:/Projects/Almost/AGENTS.md)：协作规则、范围约束、素材保护和完成标准。
3. [PROJECT-STATE.md](C:/Projects/Almost/docs/PROJECT-STATE.md)：已完成、未完成、已确认和待确认的项目事实。
4. [DESIGN-SYSTEM.md](C:/Projects/Almost/docs/DESIGN-SYSTEM.md)：已建立的视觉与交互规则。
5. 当前实现。
6. 旧任务中的讨论。

本指南是操作手册，不增加新的权威层级。如果文档与代码不一致，应明确指出冲突并核实；不要凭旧截图或旧对话恢复已经放弃的设计。

### 「00」任务负责什么

现有「00 — Project Rules / Architecture」用于核对架构与更新规则文档。它原来的审计任务明确限制了应用修改、依赖调整和 Git 操作。

适合放在这里的问题：

- 网站目前有哪些页面，哪些功能还未实现？
- 分类名称、项目数据和未来详情页路由应该如何统一？
- 哪些规则应该写入项目文档？
- 多个模块出现重复模式，是否需要建立共享组件？

单页视觉调整应进入对应执行任务。已授权的局部修改不需要先回「00」再审批；执行任务自己读取规则、完成修改，并在必要时更新文档即可。

### 4.2 创建步骤

1. 在 Almost 项目下新建任务，明确使用的项目目录。当前本地基准是 `C:\Projects\Almost`，历史任务曾使用 NAS 或其他路径，不要混用。
2. 用“编号 — 模块 / 本轮结果”命名，例如 `02.02 — 分类页 / 接入首批项目`。
3. 在第一条消息中提供本指南第 6 节的任务卡。
4. 开始时核对：当前目录、项目文档、相关文件、已有组件与待确认内容。
5. 完成后验收、记录最终决定，下一项独立目标开新任务。

也可以直接给 Codex 这样的创建指令：

> 请在 Almost 项目中新建任务「02.01 — 分类页 / 项目列表方案」。使用保存的本地项目目录 C:\Projects\Almost。第一阶段只读取三份项目文档和分类模板，输出项目列表结构与所需素材字段，暂不修改应用。不要创建分支或 worktree。

以上是你未来可以使用的指令示例；本次编写指南没有代建这些任务。

### 4.3 新对话与独立工作目录的区别

不同任务可以有不同对话上下文，但如果指向同一个本地目录，就会读写同一套文件。对话拆开后，仍应避免两个执行任务同时改 `app/page.tsx` 或 `app/globals.css`。

Worktree 是 Git 提供的独立代码检出目录，可用于并行开发；它要求 Git 仓库，并涉及后续代码整合。它与任务分类是两个维度。[OpenAI 官方 Worktrees 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)

本项目建议先采用“多个短任务、同一目录、依次修改”。需要并行实验时，再明确授权建立 worktree、指定基准并安排整合；遵守 AGENTS.md 中对 Git 修改的限制。独立目录也不能消除最终整合时的逻辑或样式冲突。

### 4.4 如何避免单类对话越积越大

继续原任务：同一处调整的尺寸微调、同一个错误的复现与修复、同一验收项尚未通过。

另开任务：

- 一个结果已经验收，即将开始另一项功能。
- 从“讨论方案”转为大规模实现，方案已整理成文件。
- 从首页转入分类页、作品内容或部署等另一类工作。
- 历史里出现很多已否定方案，开始频繁纠正旧结论。
- 需要反复粘贴长段旧消息才能说明现在做什么。

不需要等到系统提示上下文已满。也不建议每改一个数值就开新任务。拆分尺度以“可独立验收”为准，不以固定消息数量为准。

## 5. 多任务的文件归属与交接

| 文件 | 哪些任务会碰到 | 协作规则 |
| --- | --- | --- |
| `app/page.tsx` | Home、About、Contact、部分内容 | 同时只安排一个写入任务；区块级限定范围 |
| `app/globals.css` | 几乎全部 UI 任务 | 明确选择器；全局修改要检查首页与分类页 |
| `app/content/categories.ts` | 首页分类入口、分类页、分类内容 | 共享数据调整须说明双向影响 |
| `app/works/[slug]/page.tsx` | 所有分类页 | 共用模板修改验收六类；单类差异通过数据或受控变体表达 |
| `PROJECT-STATE.md` | 功能与规则任务 | 写最终状态，不追加聊天流水账；避免多人覆盖 |
| `DESIGN-SYSTEM.md` | 共用视觉或交互规则 | 只记录已确认规则，临时试验不进入 |

“负责 Home”是任务范围，不意味着独占一个永久角色；“负责 About”也不等于拥有独立代码文件。

建议交接摘要控制在一页内。复杂任务可新增 `docs/tasks/<任务编号>.md`，这是可选工作记录，不替代三份权威文档，也无需为简单修复建立文件。

```text
任务：
当前目录 / 工作环境：
最终目标：
已完成并验收：
已确定的设计决定：
实际改动文件：
当前剩余工作：
测试结果及未测试部分：
素材或截图的准确路径：
下一任务第一步：
需要保留的范围：
```

新任务应再次阅读仓库，不能只相信交接摘要；归档旧对话也不等于代码已经整合或网站已经发布。

## 7. 设计调整应遵守的现有基线

- 首页已有锁定基线。修改首页时明确指定区块；其他任务默认保留首页。
- 品牌橙色为 `--brand-orange: #ff7824`，主要字体为 Kanit，中文采用现有回退字体。
- 样式以 `app/globals.css` 中的手写选择器为主，虽加载 Tailwind v4，也不应直接切换一套新样式体系。
- 现有五个根色彩变量为 `--ink`、`--paper`、`--muted`、`--line`、`--brand-orange`。间距和动画时间尚未全面变量化，不要假设已有完整 token 系统。
- 共用 `.shell` 最大宽度 1440px；桌面两侧通常 40px，紧凑布局两侧 18px。
- 当前宽度断点为 800px。测试平板、桌面和大屏，并不意味着必须新增三个断点。
- 精选占位卡片和关于区海报的比例为 3:4。真实详情图片比例尚未建立规则，应按作品内容另行确定。
- 顶部导航沿用半透明、圆角和模糊效果，作品区使用统一白底。
- 橙色英文 Hero 标志静止时显示原始 SVG，交互时呈现 TechText 描边、拖动回弹和点击弹跳。标语解密与切山分别对应各自的模块。
- CSS 已支持减少动态效果，标语组件也检查相关偏好；Three.js 画布尚未检查该偏好。若要完善，应明确成为一个修复任务。

## 8. 从现在推进到完整作品集的建议顺序

以下为建议路线，未列为已授权开发计划。

### 第一步：统一分类与项目内容字段

解决显示名称与标准名称的关系；单独决定是否保留现有 URL。选一个资料最完整的真实作品，明确名称、分类、介绍、角色、署名、封面和内页图片。

交付：分类决定、首个项目资料表、缺失资料清单。

### 第二步：建立一个作品详情模板

先确定路由，避免与现有 `/works/[slug]` 分类路由冲突。`/projects/[projectSlug]` 可作为讨论候选，不是已确认路径。根据首个作品的真实素材确定大图、并排图片、文字与项目资料模块，只抽取确有复用价值的结构。

交付：一个完整真实项目、可复用的必要模块、可用的返回导航。

### 第三步：分类页接入真实项目列表

完善共用模板，替换档案占位区。定义空分类的展示方式，核对分类与项目对应关系。六类共享结构，内容通过数据驱动。

交付：已有项目可从分类页进入详情，暂无项目的分类有明确状态。

### 第四步：首页精选接入真实封面和链接

明确授权首页作品区修改，保留 Hero 与其他锁定区域。确定沿用滚动条带的方式以及封面裁切规则。

交付：首页精选可浏览真实作品，交互与触摸操作可用。

### 第五步：完善个人资料与联系

接入正式肖像，核对个人信息与署名，确认是否公开现有简历 PDF。根据确认版本提供下载入口。

交付：关于与联系内容准确、链接可用。

### 第六步：整站验收与发布

完成多宽度、键盘、动效偏好、图片加载和路由检查。确认正式 URL、访问范围和发布目标后再发布。

交付：已验证的发布结果与明确的剩余限制。当前指南不能证明网站已经上线。

## 9. 怎样验收开发结果

### 9.1 本地运行与检查入口

当前采用 React 19、TypeScript、vinext / Vite。Node.js 要求至少 22.13.0，声明的包管理器是 pnpm 11.22.0；`pnpm-lock.yaml` 为依据。仓库保留的 `package-lock.json` 是历史文件，不混用安装流程。

根据 [README](C:/Projects/Almost/README.md)，在项目目录运行：

```powershell
pnpm dev
```

使用 [本地预览](http://127.0.0.1:3000/)，终端需保持运行。该地址只有对应开发服务运行时才有效，本次文档任务没有重新启动或验证服务。缺依赖时再执行 `pnpm install --frozen-lockfile`，日常改字或改样式无需反复安装。

| 命令 | 检查内容 |
| --- | --- |
| `pnpm lint` | 代码规范 |
| `pnpm typecheck` | 类型 |
| `pnpm test` | 先构建，再执行 10 项渲染测试 |
| `pnpm check` | 依次执行 lint、typecheck、test |
| `pnpm build` / `pnpm start` | 生产构建 / 本地生产预览 |

新功能和跨文件逻辑修改可执行完整检查；单个样式微调优先进行针对性视觉验收。已有 HTML 测试不能证明截图效果、真实点击或手机浏览器行为正确，也无需为了简单样式调整编写机械式测试。

### 9.2 视觉与交互验收表

建议检查宽度：390px 手机、800px 断点、801px 断点外侧、1024px 平板横向、1440px 桌面、1920px 大屏。这是测试取样，不是新增断点方案。

- 目标变化是否准确出现？
- 标题和正文有无不合理断行、重叠或溢出？
- 作品完整性与主体裁切是否符合素材要求？
- 导航、分类入口、邮件、电话及返回入口是否可用？
- 键盘焦点能否看见，移动端能否操作？
- 修改共享数据或样式后，首页和六类页面是否保持预期？
- 动画是否影响阅读，减少动态效果设置下的行为是否符合任务要求？
- 控制台是否出现与本次修改有关的新错误？

开发者应明确区分“命令通过”“浏览器已检查”和“未覆盖设备”，不能把一次构建通过写成全设备验收完成。

### 9.3 当前已记录的限制

- 作品媒体与关于区海报为占位图，真实档案和详情页尚未接入。
- 分类标准名与 UI 标签仍需决定。
- 未知分类有页面内回退；项目状态后段记录其仍返回 HTTP 200，前段的状态待确认表述未完全同步。后续路由任务应实际复测再统一文档。
- 简历没有接入；正式 URL 与发布状态待确认。
- 项目状态记录三条原生 SVG img 提示和 Three.js 包体积提示；这是已有检查记录，本次未重跑构建。
- Three.js 对减少动态效果偏好的支持尚未补齐。

这些是后续排期依据，不代表每次局部任务都要顺手处理全部问题。

## 10. 日常使用速查

| 你想做什么 | 应进入的任务 | 首句重点 |
| --- | --- | --- |
| 调整切山或标语 | Home / Hero | 指出改数据、动画还是排版，保留哪些行为 |
| 改首页卡片比例 | Home / Featured | 指定端、比例、裁切和联动范围 |
| 改所有分类页 | Works / Categories | 明确共用模板、六类均要检查 |
| 加一个真实作品 | Content → Project Detail | 提供资料、图片顺序、署名和展示要求 |
| 换头像或简历 | About / Content | 给准确文件和公开展示要求 |
| 统一字体或导航 | Design System / Shared UI | 明确是全局决定，要求回归首页 |
| 预览打不开 | Runtime | 提供地址与报错，先检查服务和端口 |
| 对话开始混乱 | 当前任务交接 → 新任务 | 写最终状态、剩余事项与文件入口 |

每次最少提供五项：**改哪里、现在怎样、希望怎样、保留什么、怎样算完成。**

本指南建议每逢路由、组件结构或任务组织方式发生实质变化时更新；不把每轮微调写进来。
